There is a file in this blog's repo called `tags.ts`. Eight lines in, it says this:

> IMPORTANT: Do not add new tags without updating this file.
> Build validation will reject posts with unapproved tags.

I wrote that. It's addressed to an agent, and every agent that writes a post here reads it.

The schema that would do the rejecting is one line in a different file:

```ts
tags: z.array(z.string()).optional(),
```

Any array of any strings. It appears eight times, once per content collection. There is no validation anywhere that compares a post's tags against the approved list.

So I counted. Two hundred seventy-seven files carry tags. The approved list has eighteen entries. Forty-nine distinct tags are actually in use — thirty-two of them off-list, across sixty-four uses.

The worst one is instructive. `ai-development` declares a `replaces` array, a list of the sloppy tags it exists to absorb. `'AI'` is in that list by name. `AI` appears as a live tag on four posts.

The file names the exact mistake. The mistake is in the repo four times. The build has been green the entire time.

## A Rule in a File Is a Request

That file is a warning label. It works by being read and agreed with.

Most of what any of us gives a coding agent is a warning label. `CLAUDE.md`, `AGENTS.md`, `.cursorrules`, the system prompt, the paragraph you paste at the top of a session. All of it is text the model reads and mostly honors. Mostly is the operative word, and mostly is worse than it sounds. When a rule gets skipped and the work still looks fine, what tells you? The green build told me my tags were clean for two hundred seventy-seven files.

There is a second kind of thing, and it doesn't work that way at all. It works by shape. The instruction has nowhere to land.

Carpenters call that a jig — a fixture that holds the work so the tool can only move where the fixture allows. I'm going to use the word for the rest of this piece, and then leave the woodshop alone. The point isn't the metaphor. The point is a mechanism with two very different enforcement models, and almost everything I've built for agents sits on the weak side of that line.

## I Defined the Jig by Half

In March I reached for that word and defined it:

> A master carpenter doesn't build every piece from scratch. They build *jigs*—custom tools that hold material at the right angle, guide a cut along a precise line, make a repeatable operation fast and accurate. The jig isn't the product. It's the thing that accelerates the real work of making the product.

Read the clauses. *Accelerates. Fast and accurate. Repeatable.* Every one is about speed.

Everything after that sentence was about proliferation — agents make jigs cheap, cheap jigs breed, you end up curating a drawer of one-off fixtures instead of doing the work. I still think that's right. Eleven weeks later I described asking an agent to extract a whole methodology into a reusable template, and called that a jig too. Same definition. Same direction.

A jig has two jobs. That definition covers one of them.

## The Catalog That Makes a Cut Impossible

Before writing this I went and counted the other kind rather than trusting my memory of it.

It's a retail storefront where a model composes the page layout. A catalog file declares every named place that model may write. Twenty-eight zones across ten surfaces — home, product listing, product detail, cart, checkout, search, account, store locator, and two error states. Each entry carries two booleans: whether the composition engine may target it, and whether a merchant may author there by hand.

Twenty-seven are open to the engine. Twenty-seven are open to the merchant. They are not the same twenty-seven.

One zone under a product grid is open to the merchant and closed to the engine. One zone on the product page is open to the engine and closed to the merchant. Two booleans, two exceptions, and the reason each exception exists is that a person sat down and decided this one thing the model shouldn't touch, and this other thing the merchant shouldn't. The entire governance model for the surface is two flags in a config file that disagree exactly twice.

The cart has three zones. One above the checkout button. One below the fold, capped at two items. One empty state.

Line items, order totals, promo entry, the checkout button itself — none of them are zones. There is no address for them.

That catalog accelerates nothing. Composing a page through it is slower than letting the model emit whatever markup it wants. What it does is remove a cut.

No policy in that system says the model may not change the cart total. Nobody wrote that sentence, and nobody has to. The model receives a schema of the places it may put things, and no address in that schema reaches the total. It isn't forbidden. There's nowhere to put the instruction.

That's the difference. A warning label depends on the tool agreeing. A jig depends on the shape of what you handed it.

## Two Directions, and I Only Named One

In March, every jig I named was something an agent built for me. A script to reformat data. A workflow to pre-screen inputs. A template to scaffold a document. Agent makes the fixture, human does the work.

The zone catalog runs the other way. I build the fixture. The agent works inside it.

Both kinds have been in my repos the whole time. Only one ever got a definition. That's the tell — I had a word for the fixtures that save me time, and none for the fixtures that take away the agent's options.

The risks aren't symmetric either. When an agent builds me a jig, the failure is clutter: a drawer of one-off snowflakes, which is what I warned about. When I build one for an agent, the failure is silent. I put the fence in the wrong place and never find out, because a working jig makes the cut it prevents unobservable. Nothing errors. The bad output never appears — and neither does the good output I excluded by accident, which is the part that should worry me more. How would I ever see the page the model didn't compose because I forgot to declare a zone for it?

## The Same Mechanism Runs on My Laptop

The storefront catalog is client-scale. The same split shows up in my own dailies, and that's where it's cheap enough for anyone to copy.

I have a rule that parallel agent sessions must work in separate git worktrees, because sessions sharing one checkout switch each other's branches underneath each other and commits land on the wrong one. That rule is written in the same instructions file as everything else. It's a warning label.

It's also a hook. `PreToolUse`, matched against `Bash`, `Write`, `Edit`, and `MultiEdit`. It reads a lock directory, checks whether another live session holds the repo, and when one does, returns `permissionDecision: "deny"` with a paste-ready command for creating the worktree instead. The agent does not decide to comply with that one. The tool call doesn't run.

A second one guards reads. Images over 1400 pixels on the long edge get denied once — the hook downscales a copy to 1000px, writes it to a cache dir, and hands back the new path. Re-reading a file you already read inside a ten-minute window gets denied once too, with a note to cite from context. Both let the immediate retry through, because sometimes the re-read is legitimate.

Neither of those is sophisticated. The worktree one is 550 lines of Python, the read one 293, and both are wired up by a few lines of JSON in `settings.json`. What makes them different in kind from the paragraph above them in my instructions file isn't the code. It's that they run before the model's output reaches anything.

So which of your rules are labels, and which are geometry? Sort your instructions file into two columns sometime. Mine has two hooks in the geometry column and everything else in the other one. The tag rule sat in the label column for two hundred seventy-seven files without me or any agent that read it noticing.

## Build the Jig When You'll Make the Cut Twice

The old post buried the rule in a warning box. You built a jig only when the task was worth the setup. Agents dropping the cost of building one to near zero is what killed that discipline.

The rule survives the inversion intact. Nobody builds a jig for one cut. For one cut you clamp carefully, measure twice, go slow.

The jig I lean on hardest is ten shell commands that drive a real Chrome profile. Navigate, evaluate JavaScript in the page, screenshot, scrape to markdown, crawl, manage tabs. That's it. [The whole thing is public.](https://github.com/nino-chavez/browse-tool)

I didn't build it for a project, and that's the part that matters. It's installed permanently, on `PATH` in every shell. Because it's already there, I start every integration reaching for a real interface — a CLI, an API — and driving a human interface stays the fallback it should be. That ordering only works if the fallback exists before I need it. Built per project, it doesn't. It's a detour I don't have time for at the moment I hit a system with no API, so I either skip the work or design the whole thing around mimicry from the start.

Which raises the obvious question: why not use the MCP servers that already do this?

My own config says to prefer the shell commands because of the token footprint. It doesn't say by how much, so I measured. I started each server over stdio, completed the handshake, and called `tools/list`.

| Server | Tools | Bytes of tool schema | Approx. tokens |
|---|---|---|---|
| chrome-devtools-mcp | 29 | 23,244 | ~5,800 |
| @playwright/mcp | 24 | 18,502 | ~4,600 |

That's smaller than I'd have guessed, and the size isn't the argument anyway. The argument is *when you pay*.

Those bytes load at connection, in every session where the server is configured, whether or not the agent ever opens a page. The shell commands cost one sentence in my instructions file — a pointer to a README. Sessions that browse spend about 4,500 tokens reading it. Sessions that don't spend nothing.

I have 3,711 session transcripts on this machine. Two hundred fifty of them made a real `browse-*` call. Sixty-eight made a real call to one of those MCP servers. Whatever the right denominator is, the shape is the same: a browser is a thing I need occasionally and pay for constantly.

There's a second cost that doesn't show up in bytes. The agent already knows how to write JavaScript and read a DOM. A command that hands it a page and gets out of the way lets it use what it arrived with. A bespoke tool schema wrapping the same operations makes it learn a private vocabulary first, and that vocabulary is a fixture somebody else built for a cut I may not be making.

None of which means don't use them. If you'll genuinely make the cut once, buy the assembled thing. That isn't a compromise; that's the rule working.

## The Jig I Left on a Branch

Here's the part that undercuts everything above.

The operator card I load into every session cites one of my own scripts as a reference implementation — a mechanical check that verifies a short-form caption against the long-form post it was derived from, so a claim can't quietly change owners between the source and the summary. I wrote it because I'd watched exactly that failure happen and decided a rule wasn't enough. Turning the rule into a command was the right instinct, and it's the whole thesis of this post.

It lives on a branch called `caption-edits-0803`. Five commits of gate work, none of them on `main`. The `syndication/` directory on `main` has no gate script in it at all.

So the file that tells agents "this rule is enforced mechanically, here's the implementation" points at a check that has never run against anything I've published.

That is the same failure as `tags.ts`, one level up. The first one wrote a rule and never built the mechanism. This one built the mechanism and never installed it. Both read as geometry from inside the instructions file, and both are labels.

The silence is the whole problem. A missing warning produces a warning you notice. A missing jig produces nothing — the bad cut just doesn't get prevented, and nothing anywhere says so.

## Nothing Here Demos

I ran through a vendor capability questionnaire last week. It has a row for no-code agent builders, and two words after the row: *if available*. The next row down asks how you use AI to speed up your own development — writing code, configuring, testing, deploying.

Two rows, opposite bets. One expects a finished product a buyer can score. The other only makes sense if the surface underneath is clean enough that a general-purpose agent can work it without a human translating.

The form isn't badly designed. A rubric compares things that come out the same in every hand, and turnkey is the only category that does. But there's no cell for *we made a class of mistake structurally impossible in this surface*, because that isn't a feature. It's an absence. A cut the tool can no longer make, invisible in every demo, and the better it works the less there is to see.

## What I Still Don't Have

I don't have a validator on the tag list. Writing one is small — read the canonical keys, refine the Zod schema from `z.string()` to an enum built from them, let the build fail. It has been small the entire time the file has been claiming it already exists.

I also don't have a way to tell, from inside a session, which of my rules the agent actually followed and which it merely didn't contradict.

The drawer of snowflakes I warned about in March is still real. But it's the cheerful failure. The other one has been sitting in my repo the whole time, green.

Eighteen approved tags. Thirty-two in the wild. No error.

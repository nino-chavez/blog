Using AI well is a skill worth learning. People need practice checking its work and knowing when to step in.

But that doesn't mean everyone needs to become an AI engineer. A tool should do the job it promises. If it still needs the user to catch mistakes, it should make clear what they need to check.

---

## Checking the work is part of using the tool

I was testing a day-planning app. I wanted to know whether events from Google Calendar would reach the app on my phone. Screenshots of a pretend day couldn't show the whole path.

I asked an AI agent whether we could create test events and import them. It made the file. We put those events through Google Calendar and into the app on my iPhone. The appointments were made up, but we were testing the real connection.

I also asked an agent to test an app for running volleyball tournaments. It needed to use the screens for organizers, captains, players, and spectators. The existing tests reused one account for several roles. The agent spotted that problem and built a test with separate accounts.

Using one account cannot show whether one captain is blocked from another captain's work. We needed different accounts to check that.

The practice tournament finished, but some steps needed workarounds. It wasn't a clean pass. The report kept the problems visible.

These are skills people can practice. Give someone an unfinished task. See whether they can spot what's missing and find a way to check it. That tells us more than whether they can write a good request.

---

## Using a tool and building it are different jobs

I keep coming back to driving. A driver needs to read the road and know when to stop. They don't need to design the car. A passenger can expect to get somewhere without learning either job.

In my agent work, I do several of those jobs. I direct the agent. I also change its instructions, fix test setups, and add checks that should catch repeated mistakes.

Comparing that whole setup with an app built for one task misses the point. The app's users may have no reason to learn how to build it.

Codex itself is a product someone else built. I rely on their work to do mine.

---

## A good tool can give people less to learn

I'm helping friends who run a coffee trailer. The work is unpaid. It started with a review of their website and grew into work on a small app for posting stops and handling booking requests.

They should be able to tell customers where the trailer will be. They shouldn't need to know how I instruct the AI, put the app online, or store its data.

For an AI product, making the controls simple is only part of the job. If the user still has to check whether the AI made something up or finished an action, that work is still theirs.

In the tournament test, the person running it doesn't have to remember to turn off real emails and payments. The test setup does that. It also refuses to connect to the online app's database, where the app stores its data. We can try the tournament without contacting real participants.

Building those protections requires a different skill from reading the result. Someone running the test still needs to notice the steps that failed.

## Some mistakes belong to the tool

I've used the driving comparison before. In [“We Gave Everyone a Ferrari and Blamed the Engine”](https://ninochavez.co/blog/we-gave-everyone-a-ferrari), I called for instructors, roads, and rules.

But training alone doesn't explain the failures in my own work.

I asked an agent to [review my day planner](https://ninochavez.co/blog/rigorous-about-the-wrong-question). It produced a careful report that answered the wrong question. I had to point that out. In the coffee-app work, I also had to point out unfinished pages after earlier checks had reported success.

Catching those mistakes took work the tool had left to me. Being able to do that work doesn't prove the tool is ready for someone who can't.

These sessions don't tell me whether an agent built for those tasks would have done better. We didn't run that comparison. They show what this way of working still asked of me.

---

## Say what the user still has to do

Before I rely on an agent, I want to know:

- What mistakes will I need to catch?
- What can I do if something goes wrong?
- How will I know the job is finished?

The answers tell me what I need to learn. They also tell the builder which jobs still fall to the user. A product that needs an expert to catch its mistakes should say so before someone relies on it.

I can choose to spend time under the hood of my own systems. My friends should be able to publish a coffee stop and get back to serving coffee.

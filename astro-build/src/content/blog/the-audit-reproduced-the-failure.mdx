The audit announced that verification was complete: 119 of 118 findings.

That was not a typo. The workflow had counted rows in a journal instead of distinct findings. Stopped and restarted runs had written duplicate rows. Verification was still running.

I had asked a fleet of agents to read a project’s session history and find where the work had backtracked, regressed, or needed to be re-steered. The fleet found useful material. Then its own bookkeeping and verification rules reproduced the failure it was supposed to examine.

The useful lesson is not “do not use agents for audits.” It is narrower: the same process cannot design the sample, grade the labels, and report the rate without an independent check. Extraction, counting, and verification are different jobs.

---

## The first bad number came from counting attempts as work

The audit had a journal. Each agent attempt could append a row. When a run was stopped and restarted, the new attempt wrote another row for the same finding.

The status report counted those rows as completed work. That is how the workflow reached 119 verified findings inside a set of 118.

Those two things answer different questions.

| Artifact | What it can establish | What it cannot establish |
| --- | --- | --- |
| Agent transcript | An agent was started and produced text | The task’s conclusion is correct |
| Journal row | An attempt recorded an event | The event was counted once or finished |
| Tool exit code | A command returned successfully | The intended runtime property is true |
| Verification record | A claim was checked against named source material | The entire workflow is complete |

The system had records of all four types. It kept promoting each one into the next. A row showing that an attempt ran became evidence that a finding had been verified.

<PullQuote>
Activity is evidence that work was attempted. It is not evidence that the work exists in the state you care about.
</PullQuote>

The fix was mechanical. Count stable finding IDs, not journal rows. Keep the retries because they explain cost and failure history, but do not let them become extra findings.

---

## The final receipt left out the abandoned work

When the workflow completed, it produced a neat receipt with an agent count and a token count. The receipt described the final logical run.

It did not describe the investigation that produced that run.

Before that receipt existed, work had been launched, cancelled, and launched again under different model settings. Changing those settings changed the cache key, so some verification work ran again. The abandoned attempts still consumed time and quota. They simply disappeared from the final summary.

I went back to the raw parent and agent logs. After deduplicating cumulative usage rows by message ID, they record 334 million tokens. About 89% were cache reads. That number is not an API bill, and I cannot turn it into one honestly from these logs.

The plan impact is concrete. The run exhausted my intraday allowance, consumed about a fifth of my weekly allowance, and used 40% of my model-specific allowance. The cost I could observe was the work displaced by a burned session window.

The receipt missed that because it only knew about the branch that finished. A reliable ledger has to keep every attempt, attach it to a stable finding ID, and derive completion from the findings rather than from the last visible run.

---

## The verification filter manufactured the finding

The accounting errors explained why the work looked complete when it was not. The sampling error changed what the audit claimed to have learned.

Reader agents had labeled each candidate event: the operating packet would have prevented it, might have helped, or would not have helped. Those labels were useful for deciding where to look. They were not evidence yet.

The synthesis later turned the label distribution into a rate: the packet named the principle, and the failure happened anyway. It was a compelling story. The verification filter had created it.

The filter selected regressions and rework, plus every event already labeled “the packet would have prevented this.” That last bucket received total scrutiny. The comparison buckets did not.

| Reader label | Population | Transcript-verified | Sampling rate |
| --- | ---: | ---: | ---: |
| Would prevent | 44 | 44 | 100% |
| Would partially prevent | 248 | 70 | 28% |
| Would not prevent | 217 | 55 | 25% |

The fully audited bucket shrank from 44 candidates to 35. The lightly sampled buckets kept most of their original labels. The synthesis then compared the sizes of all three buckets and reported the difference as a finding.

That was not a weak sample. It was a comparison manufactured by the selection rule.

What survives is a floor: 35 transcript-verified events where the packet would clearly have prevented the failure. No population rate survives. The other buckets need comparable sampling under the same decision rule before any “times in ten” claim is measurable.

The selection rule did not merely weaken the conclusion. It created the comparison the conclusion depended on.

---

## The fleet found material, not a verdict

The failed rate does not make the extraction useless.

The fleet pulled a scattered session history into a dataset I could inspect. It surfaced real events. Thirty-five preventable failures survived direct transcript review. That is useful work.

It is not a verdict on one model, either. This was not a controlled comparison between models, prompts, or orchestration systems. The same process extracted the candidates, designed the filter, interpreted the results, and reported the rate.

That is the boundary the run can support:

```text
agents        → extract candidates
code          → deduplicate and account for attempts
independent review → verify source claims and decide what survives
```

Those roles can be performed by people, programs, or different models. The important part is separation. The process that designs the verification filter does not get to certify the rate that filter produces.

---

## The next audit gets a smaller receipt

The next version does not need more agents. It needs a receipt that makes the boundary visible.

For every conclusion, the receipt should show three things:

| Extracted | Counted | Verified |
| --- | --- | --- |
| The candidate event and who produced it | The stable event ID and deduplicated attempt history | The source checked, the surface observed, and the exact conclusion that survived |

If any cell is blank, the conclusion stays a candidate. It can still be useful. It cannot be a rate, a completion claim, or a deployment decision.

That is a modest artifact: a row, a source link, a state transition. It is more valuable than another synthesis report because it shows exactly where a candidate became evidence.

The first audit produced 119 of 118. The next one should be unable to write that sentence.
